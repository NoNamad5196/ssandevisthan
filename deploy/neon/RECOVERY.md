# Rollback and recovery runbook

This implements operations contract §§13/15/17 within the authorized Neon replacement. The incident owner/operator is repository owner **NoNamad5196**. An intentional production rollback or data restore requires an explicit incident decision. Record time, affected release, decision, reviewed target, checks and uncertainty in a private incident report without credentials, images, prompts or merchant HTML.

## Retained releases

Each backend deployment workflow uploads `backend-<git SHA>` for **7 days**. API, worker and sweep share this Node24 Linux ARM64/glibc deployable unit. `release-manifest.json` records every file's SHA-256/length, commit, runtime, migration checksums, policy versions and an allowlist of actual nonsecret deployment settings. Credentials are referenced by name only. Frontend artifacts remain independently retained for7 days. Expired artifacts make that rollback path unavailable; rebuilding dependencies is not the same saved artifact.

Retrieve artifacts only from the owner's repository and a successful, reviewed deployment run. Checksums verify integrity, not an untrusted author's identity. Current encrypted secrets remain authoritative; rollback must not revive revoked credentials. Missing deployment configuration in a locally generated manifest is explicitly null, not proof of the live server settings.

Artifact retention begins with this workflow revision. Earlier deployments did not retain an exact backend binary artifact; they are not retroactively certified as rollback targets. `build-provenance.json` records the build's commit, dirty state and entry-point checksum; sealing requires the same commit and retains either build-time or seal-time dirty state. Production verification/deployment rejects dirty artifacts on every path. Only the explicitly labelled local synthetic drill may inspect them. Review GitHub's actual storage allowance before retaining more releases; this workflow never enables paid storage.

## Code rollback

1. Stop paid admission/calls using the DB budget kill switch and `PAID_EXECUTION_ENABLED=false`. Preserve outstanding reservations. Stop competing deployments. Already sent provider requests may still incur cost.
2. Drain active searches or terminate through the normal fenced transaction path. Never delete queue rows to make the drain counter healthy. Reconcile unknown outcomes separately.
3. Retrieve the reviewed artifact: `gh run download <run-id> --name backend-<SHA> --dir .cache/rollback/<SHA>`. Download matching frontend artifacts separately if needed.
4. Verify bytes with `node deploy/neon/release.mjs verify .cache/rollback/<SHA>`. Inject `DATABASE_URL` and run `node deploy/neon/rollback.mjs .cache/rollback/<SHA>`; default mode is **read-only dry-run**. It rejects corrupt bytes, unknown schema changes, enabled paid execution and undrained searches. Exact migration equality is conservative: additional/altered schema requires compatibility work or a forward fix. No down migration runs.
5. Review whether older code reintroduces a security/source-policy defect. Compare saved nonsecret settings with current settings. Old source permissions, models, verification flags, credentials and paid enablement are never automatically restored. Use a forward fix if current restrictions cannot be preserved.
6. After explicit incident authorization, inject stable `NEON_BACKEND_ENV_JSON`, `NEON_API_KEY`, and `ROLLBACK_APPROVED_SHA=<reviewed SHA>` and add `--apply`. This deploys saved code and checks health with paid execution off. It changes no schema, queue, schedule or budget. Do not execute this on production merely for a drill.
7. Verify owners/sessions, historical snapshot versions, uncertain reservations and cleanup. A canary must independently satisfy its prerequisites. Record remaining uncertainty; do not promise zero loss or a recovery deadline.

Sealing and deploying require the same strict persisted-settings schema; empty JSON, missing authentication/worker/schedule keys, malformed origins, unknown overrides and unsafe paid enablement are rejected. Verification independently validates the saved public settings. Manifests contain only allowlisted nonsecret values and secret reference names. Rollback `--apply` additionally binds the supplied PostgreSQL URL to the immutable production project/branch/database and the function origin using read-only official Neon endpoint/function/database metadata, before opening that DB connection. Different test endpoints, database names, roles and URL routing overrides are rejected. A healthy dry-run against an unrelated database cannot authorize a production deployment.

## Metadata recovery into a new database

`recovery.mjs` exports `exportRecoverySnapshot(client)` and `restoreRecoverySnapshot(client,envelope)` for an operator-controlled PostgreSQL connection. No automatic production export or external backup destination is configured. First select an access-controlled location, enforce expiry deletion, and verify free quota. No production user rows were exported in this drill.

The consistent read-only export contains unexpired search metadata, related merchant evidence/snapshots, owner IDs, known pilot ledger and reservations. It excludes image bytes/object keys, jobs/leases/checkpoints, refresh-session secrets, environment secrets and IP hashes. Exports expire at the earlier of1 hour and the earliest included search expiry. A backup scheduler must delete each export by that timestamp. Restoring before expiry never extends original record TTLs. Post-export provider activity is a possible loss interval requiring reconciliation.

Restore order is schema/migrations/RLS, validated metadata, then functional checks. Only a new empty DB with the exact schema is accepted. Expired/tampered exports and populated targets are rejected. Terminal state and snapshot bytes/versions remain unchanged. Interrupted searches become `FAILED/OPERATOR_STOP` with re-upload guidance; no upload or runnable job is imported. STARTED provider calls become UNCERTAIN while reservations remain held, including orphan reservations of expired searches. Known spend is preserved; verification flags are cleared and paid execution stays disabled until reconciliation. Missing images or anonymous refresh sessions are not fabricated.

## Reproducible drill and scope

Run `node deploy/neon/build.mjs`, `node deploy/neon/release.mjs create`, then `node deploy/neon/recovery-drill.mjs`. The backend workflow performs this drill before production changes and retains only its aggregate report as `backend-recovery-<SHA>`. No cloud credential is injected into that step.

Three separate local PGlite PostgreSQL databases exercise a synthetic metadata file round-trip, schema/data/RLS restore, fencing, kill switch, TTL and the actual worker handler with outbound fetch denied. The exact API/worker artifact is copied, deliberately damaged, rejected and restored to its original checksum. Evidence is `.cache/recovery-drill-latest.json`; a checked-in aggregate example is `docs/deployment/recovery-local.json`.

This is **actual isolated local PostgreSQL recovery**, not LIVE product search or a cloud runtime rollback. ARM64 bytes are verified/copied, not executed on Windows. Production resources and data stay untouched; no new cloud resource or paid call is used. Cloud staging rollback, an automatic private backup destination/expiry scheduler, production recovery canary, and measured RPO/RTO remain unverified and must remain open in the release checklist.
